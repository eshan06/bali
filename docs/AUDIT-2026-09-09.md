## Confirmed findings

### [CRITICAL] Shields are never re-applied after Screen Time permission is restored mid-session — teacher's grid flips back to green while nothing is shielded

`ios/Bali/Bali/Core/FocusEngine.swift:160` · iOS · focus engine

The heartbeat's "focused" branch short-circuits when the local state is already `.focused`, so `applyFullFocus()` is never called again. Because the client also never handles the server's `revoked` state (`default: break`), the local state stays `.focused` through the whole permission-off/permission-on cycle, and the shields that iOS dropped are never restored.

**Fails when:** Student taps in at 9:00 with Screen Time on (shields applied, state `.focused`). At 9:05 they turn Screen Time off in iOS Settings — iOS drops the ManagedSettings shields. The next heartbeat sends `permissionOk: false`; the server sets the participation to `revoked` (domain.ts:556-557) and returns `state: "revoked"`, which the client's switch ignores (`default: break`, FocusEngine.swift:167), so the local state remains `.focused`. At 9:07 the student turns Screen Time back on. The next heartbeat sends `permissionOk: true`; the server flips the row back to `focused` and emits `permission_restored` (domain.ts:568-576), returning `state: "focused"`. The client hits `if case .focused = state {}` — a no-op — so `applyFullFocus()` is never called. For the remaining 43 minutes the phone is completely unshielded, the student's app shows the ticking focus arc, and the teacher's live grid shows a green "Focused" chip. A two-tap, fully reversible bypass that leaves no visible trace on either surface.

**Fix:** Do not use the local state as a proxy for "shields are on". Track the real thing and reconcile every heartbeat: if the server says `focused` and `screenTime.shieldsApplied == false` (or `permissionOk` just flipped back to true), call `applyFullFocus()` unconditionally. Also add an explicit `case "revoked"` that drives a visible client state so the student's screen stops claiming focus while permission is off.

### [HIGH] Student-supplied timestamps are trusted unbounded into the past — a backdated emergency unlock disappears from the teacher's unlock report, and a backdated tap-in inflates focus minutes without limit

`apps/api/src/domain.ts:651` · API · domain/reports

emergencyUnlock() and tapIn() accept a client-chosen `at`/`tappedAt` and clamp only the future side, so the student the record is about controls the timestamp of their own audit row; unlocksReport filters by that timestamp and focus-minute math subtracts from it.

**Fails when:** A student sets their iPhone date back (a well-known way kids defeat on-device time limits) or simply POSTs `{"clientEventId":"...","at":"2026-07-01T09:00:00Z"}` to /v1/sessions/:id/unlock. The unlock row is written with that `at`. unlocksReport (reports.ts:91 `gte(s.unlocks.at, since)`, since = Monday of this week / 1st of this month) never returns it, and the 6-week sparkline bucket index (reports.ts:108) falls outside 0..5 and is discarded — the teacher's W8 Unlocks table and its CSV export show the emergency never happened. Symmetrically, POSTing /v1/sessions/:id/tap-in with `{"tappedAt":"2026-08-01T00:00:00Z"}` writes both participations.tappedInAt and the `tapped_in` event at that time; focusMinutesByStudent then computes `endAt - since` (reports.ts:328) as ~57,000 minutes, which lands in sessionRecap.medianFocusMinutes, classOverview.medianFocusMinutes, the class-average bar in focusMinutesReport, and the student's own week bars / streak (routes/student.ts:267). Nothing clamps either value to [session.startedAt, now].

**Fix:** Clamp both to the session window before persisting: `const at = clamp(opts.at ?? now, session.startedAt, now)` (and the same for tappedAt), rejecting or silently flooring anything earlier than session.startedAt. Offline replay still works — a genuine offline unlock always falls inside the session it belongs to.

### [HIGH] A student carrying a standing "no device" mark who taps in stays "No device" on the teacher's grid forever, even while shielded and heartbeating

`apps/api/src/domain.ts:510` · API · domain/reports

startSession seeds participations with noDevice: true for every defaultNoDevice member, and tapIn never clears the flag; deriveParticipantState puts no_device ahead of everything, so the teacher sees "No device" for a student who is in full focus.

**Fails when:** Teacher marks Hana defaultNoDevice (she usually has no phone). Next period Hana brings her phone, taps the desk tag, the client applies full focus and heartbeats every 30s. startSession already inserted her participation with noDevice: true (domain.ts:226); tapIn takes the `existing` branch and sets only state/tappedInAt/lastSeenAt/tapClientEventId, leaving noDevice true. serializeParticipant feeds noDevice into deriveParticipantState, which returns 'no_device' unconditionally and first (states.ts:81-83), so the grid chip, counts.no_device, and every SSE participant frame say "No device" while she is actually focused. sessionRecap then `continue`s her out of focusedCount / studentsTappedIn / medianFocusMinutes into noDeviceNames (reports.ts:404-408), and studentSessionHistory labels her day "No device that day" (reports.ts:497-499) — which is also what her parent sees through the parent link. Meanwhile /v1/student/home hands the student the raw stored state 'focused' (routes/student.ts:94), so student and teacher are told two different things about the same device. Only the teacher manually toggling no-device off repairs it; the student has no way to.

**Fix:** Clear the flag on a real tap-in: add `noDevice: false` to the tapIn update (and to the insert path), and append a `no_device_cleared` event so the timeline explains the change. A tap-in is proof of a device; a standing mark is only a default.

### [HIGH] Rate-limit key is a caller-controlled, unvalidated header — every limit is trivially bypassable, including on the unauthenticated public routes

`apps/api/src/app.ts:51` · API · routes/authz

The global rate-limit keyGenerator buckets by the raw `Authorization` header, which the client chooses freely and which the public routes never validate, so any caller gets a brand-new quota bucket per request simply by varying the header.

**Fails when:** An unauthenticated attacker hits `GET /v1/public/parent/<guess>` (or `/v1/public/tags/<guess>`) 100k times/minute, sending `Authorization: Bearer a1`, `a2`, `a3`… Each distinct string is a distinct key, so the `max: 120, timeWindow: '1 minute'` cap (public.ts:17, :38) never fires — the `req.ip` fallback is only reached when NO header is sent. Each request runs a DB query (`parentLinks.findFirst` + full `parentView`, which fans out ~10 queries), so one host with no credentials can saturate the Postgres pool. The same trick removes the ceiling on `POST /v1/auth/bootstrap` (auth.ts:12) and on every `limited(n)` student route, since @fastify/rate-limit runs on onRequest — before `authenticate` — so junk tokens are counted into throwaway buckets rather than the caller's real one.

**Fix:** Key by identity only when the token is verified, and fall back to IP for everything else, e.g. `keyGenerator: (req) => req.identity?.sub ?? req.ip` (with authenticate moved to onRequest) or, minimally, `keyGenerator: (req) => \`${req.ip}:${req.headers.authorization ?? ''}\`` so an unverified header can only narrow a bucket, never escape the IP one.

### [HIGH] A student removed (or leaving) mid-session stays shielded, but their emergency unlock is rejected 403 and silently discarded

`apps/api/src/domain.ts:548` · API · routes/authz

`heartbeat` gates only on an existing participation row, while `emergencyUnlock` and `refocus` gate on an ACTIVE membership — so once the membership disappears the phone keeps being told the session is live (shields stay on) but the exit endpoint starts returning 403.

**Fails when:** Sam taps in (participation row created). The teacher then taps Remove on the roster — `removeMembership` deletes the membership row and never touches `participations` or `passes` (domain.ts:910-911). Sam's phone keeps calling `POST /v1/sessions/:id/heartbeat` every 30s; it succeeds (only a participation is required) and returns `state: 'focused'` with the live `endsAt`, so FocusEngine keeps the full-focus shields applied and re-arms the watchdog (ios/Bali/Bali/Core/FocusEngine.swift:143-168). Sam then hits Emergency Unlock: shields drop locally, but the queued `POST /v1/sessions/:id/unlock` gets `403 not_member` from `requireActiveMembership`, and the client's `catch let err as APIError where (400 ..< 500)` branch drops the queued item permanently (FocusEngine.swift:210-211). The unlock is recorded nowhere — not in the teacher's timeline, not in `/v1/reports/unlocks`, not in Sam's own `/v1/student/history`. `POST /v1/sessions/:id/refocus` 403s the same way, so Sam also cannot re-enter focus. The identical sequence fires when the student uses the app's own "leave class" path (routes/student.ts:320).

**Fix:** Make the lifecycle consistent: on `removeMembership` / declined membership / student leave, end the student's open participation (`state: 'ended'`) and close any active pass in the same transaction, and either add the membership check to `heartbeat` (returning a terminal `ended` session so the phone unshields) or drop it from `emergencyUnlock`/`refocus` so a recorded participant can always record their exit.

### [HIGH] "Revoke link" swallows the failure and closes — a live parent link the teacher believes is dead

`apps/web/src/app/app/classes/[id]/roster/page.tsx:83` · Web portal

revokeParent() catches every error from DELETE /memberships/:id/parent-link, discards it, and unconditionally closes the dialog, so a failed revoke is indistinguishable from a successful one — and this is the only revoke affordance in the whole portal.

**Fails when:** Teacher mints a parent link, then decides not to share it and clicks "Revoke link". The DELETE returns 500 (or hits the 15s ApiError timeout, or the laptop's Wi-Fi drops for a second). The catch block runs, `setParentLink(null)` closes the overlay with no toast and no error, and the teacher walks away believing the link is dead. The token is still valid, and the unauthenticated /p/<token> page keeps serving that student's focus history, live status, and emergency-unlock counts to anyone holding the URL. There is no active-parent-link indicator on the roster and no revoke entry point outside this just-minted overlay, so the teacher can neither see the mistake nor retry — the privacy page (apps/web/src/app/privacy/page.tsx:81) explicitly promises the link "can be revoked at any time by the teacher".

**Fix:** Await the delete and only close on success: on failure keep the overlay open and surface it through the existing ErrorToast (`setLinkError('Couldn’t revoke that link — it is still active. Please try again.')`), leaving the Revoke button live for a retry. Separately, the roster row should show whether an active parent link exists so revoke is reachable after the mint dialog is dismissed.

### [HIGH] A transient (non-401) /me failure signs the teacher out into a /login page that cannot sign them back in

`apps/web/src/lib/auth.tsx:127` · Web portal

AuthProvider treats any loadMe() rejection as "not a teacher", which makes /app redirect to /login — but the Amplify session is still valid, so both sign-in buttons on /login throw UserAlreadyAuthenticatedException and the teacher is stuck with no sign-out escape.

**Fails when:** Teacher loads /app during a brief API hiccup (a 500 from GET /v1/me, a 15s request timeout, or a CORS/LB blip — anything that is not a 401, since 401 is handled separately by the unauthorizedHandler which does call amplifySignOut). loadMe() rejects → `.catch(() => setTeacher(null))` → AppShell's effect (`apps/web/src/app/app/layout.tsx:13`) does `router.replace('/login')`. That is a client-side navigation, so AuthProvider stays mounted and loadMe never runs again. On /login the teacher types their password: `amplifySignIn` calls `assertUserNotAuthenticated()` (node_modules/@aws-amplify/auth/dist/esm/providers/cognito/utils/signInHelpers.mjs:664-676), which throws "There is already a signed in user." — rendered verbatim under the Password field by login/page.tsx:32. "Continue with Google" throws the same error from signInWithRedirect, and it is fired as `void signInWithGoogle()` with no catch, so that button does nothing at all. The portal is unreachable until the teacher happens to hard-reload the page; mid-class this is the live grid going away with a login form that rejects the correct password.

**Fix:** Distinguish "no session" from "couldn't reach the API": keep an `authError` state, and on a non-401 loadMe rejection leave `teacher` untouched and render a retry state instead of nulling it (the 401 path already tears the session down centrally). Additionally, on /login, when `getCurrentUser()` resolves but `teacher` is null, call `amplifySignOut()` before attempting `signIn`, and catch `signInWithGoogle()`'s rejection so it can never fail silently.

### [HIGH] SSE events are held in a single `lastEvent` slot, so concurrent events are dropped and their toasts never appear

`apps/web/src/lib/live.ts:68` · Web portal

applyMessage stores every 'event' frame into one state slot, and the live page's seenEvents guard makes the loss permanent — when two event frames land in the same React batch only the last one ever reaches the toast effect.

**Fails when:** The stream reader parses every frame in one `reader.read()` chunk synchronously (live.ts:141-160), so two SSE `event` frames delivered in one TCP chunk produce two `setLastEvent` calls in the same React 18 batch — only the second survives to render. The live page's effect then does `seenEvents.current.add(lastEvent.id)` for the survivor only, and the dropped event is never re-delivered. Concretely: two students in the same class hit Emergency Unlock within the same instant (fire drill, a shared upsetting text), or two students' heartbeats report `permissionOk:false` in the same second (apps/api/src/domain.ts:558), or the pass sweeper expires two passes in one pass of its loop (apps/api/src/domain.ts:790-823, each iteration writing to the same socket microseconds apart). The teacher gets exactly one sticky orange "used Emergency Unlock" toast instead of two — on the surface whose entire job is alerting them. The chip still flips (pulse comes from the 'participant' frame), but the toast, its timestamp, the reason subtitle and the "Open student" action for the first student are gone for good.

**Fix:** Make the event channel a queue rather than a slot: `setEvents(prev => [...prev, msg.event])` (bounded, e.g. last 50) and have the live page drain and mark-seen every unseen entry, instead of reading a single `lastEvent`. That also removes the need for the seenEvents Set to be the only de-duplication.

### [HIGH] The start-session card's "Ends at" and "Policy" fields are inert divs styled as dropdowns

`apps/web/src/app/app/classes/[id]/live/page.tsx:421` · Web portal

Both fields render a bordered box with a trailing ChevronDown affordance but are plain <div>s with no onClick, no <select>, and no dialog — the teacher cannot change either value from anywhere in the web portal.

**Fails when:** It is 10:50 and the class's 10:45 bell has already passed. The teacher opens /app/classes/<id>/live and sees the start card showing "11:40 · today’s bell passed · +50 min" with a chevron, and "Focus ▾" next to it. They click the chevron to shorten the session to the 25 minutes actually left in the period, or to pick a different policy — nothing happens, because both are non-interactive divs (the only ChevronDown occurrences in the entire codebase are these two, and @radix-ui/react-select is a dependency that is never imported anywhere). Their only options are to start a 50-minute session that shields every phone past the next period's start, or to start it and then click "Extend" — which only adds time, never removes it. The product's own standard ("if the UI promises something the code does not do, that IS a bug") is violated twice on one card.

**Fix:** Either wire them up — an `<input type="time">` for the end time (feeding bellIso) and a `<select>` over the loaded policies (feeding the `policyId` already sent at line 390), matching what /app/classes already does — or drop the ChevronDown icons and the input chrome so the card reads as the static summary it actually is.

### [HIGH] applyFullFocus() silently drops allow-list CATEGORY and web-domain picks — a category-only selection shields everything the student meant to keep

`ios/Bali/Bali/Core/ScreenTime.swift:80` · iOS · focus engine

`FocusAllowList.count(of:)` counts applications + categories + webDomains, but `.all(except:)` is passed only `selection.applicationTokens`. A student whose one-time pick contains categories (or only categories) passes the `count > 0` gate and then gets `.all(except: [])` — a total shield, including the apps they explicitly chose to keep open.

**Fails when:** At onboarding the student opens the FamilyActivityPicker and taps the "Education" and "Utilities" category rows (the picker's most natural gesture — one tap selects a whole category). `count(of:)` returns 2, so the button reads "2 selected" and the branch at line 79 is taken. But `selection.applicationTokens` is empty, so line 80 evaluates to `.all(except: [])` — every application category is shielded. During the next session the Calculator and Notes they thought they had allowed are blocked, directly contradicting the onboarding copy ("Choose the few you always want — like Camera, Notes, or a calculator", OnboardingView.swift:79) and the in-session copy ("every app pauses except the few you chose", JoinView.swift:155). The failure is silent — no error, no indication the pick was ignored.

**Fix:** Expand category tokens into the application tokens they cover before building the exception set, or gate the branch on `selection.applicationTokens.isEmpty == false` and tell the student at pick time that category selections cannot be honoured. Either way the count shown in the UI must count only what `applyFullFocus()` will actually exempt.

### [HIGH] Focus starts and the app claims "Focused" even when Screen Time authorization is denied — the guard fails silently and Settings copy says the opposite

`ios/Bali/Bali/Core/ScreenTime.swift:78` · iOS · focus engine

`applyFullFocus()` early-returns when authorization is not approved, leaving `shieldsApplied == false` and returning no signal. `FocusEngine.startFocus` ignores this entirely: it sets `state = .focused` and the flagship focus screen renders. The app tells the student they are in full focus while nothing whatsoever is shielded, and the promised "status-only" mode from the onboarding denied path does not exist in code.

**Fails when:** A student takes the onboarding "Join without focus (status-only)" exit (OnboardingView.swift:92) or later turns Screen Time off. They tap the desk tag. `startFocus` POSTs the tap-in (recorded as `focused` server-side), calls `applyFullFocus()` which returns immediately at the `guard`, then unconditionally sets `state = .focused` and presents FocusActiveView with the 244pt arc, the countdown, and the line "Works without Wi-Fi. Releasing early does nothing." Nothing is shielded. Meanwhile SettingsView tells that same student "Focus can't start until it's back on" — a promise the code does not keep. (The server does mark them `revoked` within 30s, but the client's heartbeat switch drops that state, so the student's screen never corrects itself.)

**Fix:** Make `applyFullFocus()` return a Bool (or throw) and have `startFocus`/`resume`/`refocus` branch on it: with permission denied, either refuse to enter `.focused` and show the honest "permission off / status-only" screen, or enter a distinct state whose copy does not claim apps are paused. The tap-in should still be recorded so the teacher sees the honest `revoked` chip.

### [HIGH] Home banner claims "Focused until HH:MM" with a ticking arc for any live session in the student's class — including one they never tapped into

`ios/Bali/Bali/Features/HomeView.swift:331` · iOS · focus engine

`liveClass` selects any active-membership class with an open session and never inspects `mine`. `bannerTitle(for:)` then returns "Focused until <time>" for every non-unlocked case. A student who has not tapped in — or whose participation is `not_joined` or `revoked` — sees the Focused banner and the live MiniArc while zero shields are applied.

**Fails when:** Teacher starts the 9:00 session. The student opens Bali at 9:02 but has not tapped the desk tag yet. `student/home` returns `mine.state == "not_joined"` (routes/student.ts:94), so `HomeModel.load` skips the resume block and `focusPresented` stays false — the normal Home content renders. `liveClass` matches the class (it only checks `live != nil && membershipStatus == "active"`), so the banner shows a 36pt animated MiniArc counting down plus "Focused until 9:50". ### [HIGH] Pass expiry never restores shields locally — "shields return automatically" is false offline and up to 30s late online

`ios/Bali/Bali/Core/FocusEngine.swift:157` · iOS · focus engine

Granting a pass clears the shields, but nothing on the device ever brings them back at `passEndsAt`. There is no local timer for pass expiry; the only restore path is a heartbeat response of `state == "focused"`. The pass chip promises "shields return automatically" and the focus screen promises "Works without Wi-Fi" — with no network, the shields never return for the rest of the period.

**Fails when:** Teacher grants a 5-minute pass at 9:20. The client's heartbeat sees `state: "pass"`, calls `screenTime.clearShields()`, and enters `.pass(endsAt: 9:25)`. The student walks into the hallway and loses Wi-Fi. At 9:25 the pass countdown hits 0:00 on screen; `checkSessionOver()` deliberately skips the pass case (`!isPass`, FocusActiveView.swift:221) and no other code path re-applies shields. Every subsequent heartbeat fails and returns early at FocusEngine.swift:140-142 ("offline: focus continues"), so `applyFullFocus()` is never reached. The phone stays fully unshielded for the remaining 25 minutes of class while the app displays a pass chip that says shields return automatically. Even on a good network the restore is up to 30 seconds late and depends entirely on the server's sweeper having flipped the row.

**Fix:** Schedule a local restore when entering `.pass`: a timer (and a `checkSessionOver`-style tick in FocusActiveView) that fires at `passEndsAt`, calls `applyFullFocus()`, and moves the state back to `.focused` without waiting for the server. The heartbeat should then only reconcile, not be the sole mechanism.

`ios/Bali/Bali/Features/HomeView.swift:369` · iOS · student UI

`ios/Bali/Bali/Features/OnboardingView.swift:110` · iOS · student UI

### [HIGH] Stashed sign-up name survives sign-out and binds the next account to the previous student's roster row

`ios/Bali/Bali/Core/Auth.swift:142` · iOS · student UI

`stashName` is written before the sign-up network call and cleared only on a successful profile load; `signOut()` removes the dev token but not the stash, so the next Cognito account signed in on that device is bootstrapped with the previous person's first/last name — and the API adopts any unclaimed roster student with a matching name.

**Fails when:** On a shared classroom iPad, Maya Chen taps "Create account", so `stashName(first: "Maya", last: "Chen")` runs; she then hits the confirmation-code screen and taps "Use a different account" (SignInView.swift:164 → `auth.signOut()`), or the sign-up errors out. Diego signs in with his own confirmed Cognito account. `loadProfile()` finds the stale stash and POSTs auth/bootstrap as `{firstName: "Maya", lastName: "Chen"}` under Diego's sub; apps/api/src/auth.ts:168-181 finds the unclaimed roster row for Maya Chen and sets `cognitoSub` to Diego's. Diego now holds Maya's memberships and history, the teacher's grid labels him "Maya Chen", and Maya can never claim her own row (it is no longer `isNull(cognitoSub)`).

**Fix:** Clear `bali.pendingFirstName`/`bali.pendingLastName` in `signOut()` (and on any auth error path), and tag the stash with the Cognito sub it was captured for so `loadProfile` ignores a stash belonging to a different identity.

### [HIGH] JoinView enrolls the student before showing the "preview" they are supposed to consent to

`ios/Bali/Bali/Features/JoinView.swift:136` · iOS · student UI

The 8th typed character fires POST /v1/join, which creates the membership and writes a member_joined event; the card rendered afterwards is a receipt, not a preview, and its button says "Done" — the file's own header claims the opposite. (Confirmed; already tracked as a P0 item in docs/ROADMAP.md.)

**Fails when:** A student mistypes one character of the code from the board and it happens to match another teacher's class. **Fix:** Add a read-only preview lookup (GET /v1/classes/preview?code=) that returns the same class/teacher/schedule shape without a transaction, render it on the 8th character, and only POST /v1/join from an explicit "Join class" button.

### [HIGH] A failed recap fetch traps the teacher in an undismissable full-screen spinner after every session end

`ios/Bali/BaliTeacher/T10Recap.swift:31` · iOS · teacher + core

T10RecapView renders a bare ProgressView while `recap == nil` and puts its only dismiss control ("Done") inside the `if let recap` branch; T2 presents it in a `.fullScreenCover`, which has no swipe-to-dismiss, so a failed/never-returning recap request leaves no way out.

**Fails when:** Teacher ends a session (or the bell ends it while T2 is open) → `showRecap = true` presents T10 full-screen → `GET sessions/:id/recap` fails (offline, 401 after a token refresh failure, 500, or the 15s timeout). `recap` stays nil, so the view shows a spinner with no Done button, no error, and no retry; `.fullScreenCover` blocks interactive dismissal. The teacher app is unusable until they force-quit it — at the exact end-of-class moment the product exists for.

**Fix:** Track a load-failed state and always render a dismiss affordance: put "Done" outside the `if let recap` branch, and show a "Couldn't load the recap · Retry / Done" state on failure (the web already ships `LoadError` in apps/web/src/components/bali/bits.tsx:87 for exactly this).
